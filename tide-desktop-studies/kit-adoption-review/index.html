What should return to the kit

Document the combined refinement form, live draft count, action semantics and applied context. Extract one reusable panel layout when implementation begins. Existing Field, Fieldset, Choice, Button, Badge, Result summary, Empty state and disclosure already cover the individual controls and states.

This records the decisions. It does not ship new component CSS or change the approved prototype. The proposed tide-filter-panel name is a candidate API, separate from the shipped component manifest.

The approved Unified Search 1.0.2 and its dependencies remain fixed. This companion documentation uses the existing Prose and Content page components. The kit's exact file inventory is also locked, so the review lives beside the studies until a versioned adoption incorporates it.

One panel block, with a footer

tide-filter-panel is justified because the kit has no shared structure for an independently scrolling form body and an always-reachable action area. A native disclosure only reveals content; the additive Panel example does not provide this layout.

The proposed block has an optional __header, __title, __description, scrolling __body and non-scrolling __footer. Its __status-row holds Reset all and a __count; the existing full-width Button supplies Show events. These are panel elements, rather than separate live-count, reset-button and action-dock components.

  • The body uses a zero-minimum grid track and native overflow. The footer stays outside that scrolling area.
  • The footer consumes existing space 4 above and below the status row, preserving the approved 16px balance. Its row can wrap with long wording or enlarged text.
  • Reuse existing semantic color, type, target, radius, border and spacing tokens. Keep neutral dividers and the square control treatment.
  • Give the count its own panel element using the existing secondary-text role. The existing Caption uses a muted role, so substituting it blindly would change the approved appearance.
  • The host supplies native dialog or labelled aside semantics and the available height. The kit supplies inner layout, not a 75rem breakpoint, column widths or a global viewport calculation.

Proposed source homes: css/filter-panel.css in the existing tide.components.extensions layer, shared templates/filter-panel.html, and a frame generated from that source in every theme and mode. Public names, optional presentation variants and any local inputs must be registered when those files actually ship.

The interaction contract

This is a live count with deliberate apply. Typing and changing filters preview the draft. The event feed and applied URL change on Show events or Enter. Calling it automatic live-result search would promise a different behavior.

Counts and announcements

Keep one polite, atomic draft status in the panel. Update its text and the submit label together without moving focus on each edit. The applied Result summary remains the authority for the feed. Avoid making every field, badge, button and container a competing live region. Status messages should be available to assistive technology without taking focus, following W3C's status-message guidance.

Modal and desktop behavior

The flyout uses native dialog and showModal(). It needs a meaningful title, an initial focus target inside it, contained Tab/Shift+Tab navigation and focus restoration on dismissal. Preserve Cancel/Escape/backdrop rollback before closing. Do not add positive tabindex values or simulate a dialog with an unlabelled div. See the W3C dialog pattern.

The desktop rail is non-modal. Its Close action hides the rail and retains the draft; it is not Cancel. An open small-screen modal rolls back before the desktop host is restored. Preserve one live control set through this change; cloning forms creates duplicate IDs, ambiguous form ownership and divergent values.

The form can use existing classes

A standalone search Field needs no new control and no empty second column from tide-search-line. Keep that existing two-part composition available for other screens that really have an adjacent submit action.

This specimen defines form semantics using shipped classes. Its footer is deliberately unstyled as a panel: that layout is the proposed extraction. The host computes matches and handles the GET route; this is not a working search service.

Download the HTML specimen. An externally positioned submit uses form to retain the same owner. An input outside that form needs its own association; a fieldset's form attribute does not automatically associate every child. See MDN's form-owner reference.

What stays in the app

Matching words, inclusive Albuquerque dates, OR categories, event data, GET destinations, preview selection and history/reading-position restoration remain host behavior. The kit documents how that behavior meets its controls; CSS does not pretend to supply matching or routing.

Margin Reveal, the fixed event-detail position, header alignment, independently bounded desktop panels, the 75rem breakpoint and the 24px plus native-gutter clearance stay in the app shell. The measured scrollbar width is a runtime value, not a theme palette or spacing token. Keep native scrollbars and remove the measurement below desktop as the approved implementation does.

Motion timing, visual-viewport/keyboard positioning and responsive node orchestration also stay host-owned. Future asynchronous matching would need a separately specified pending, failure and stale-response contract; the approved local count is synchronous. Do not invent those as already-shipped states.

A controlled adoption sequence

  1. Keep the approved prototype, original kit and current dependency files pinned. This review is additive documentation only.
  2. Implement the one panel block and the shared form specimen in an additive kit release. Register CSS, HTML, elements, states and integration behavior in the existing manifest and component documentation.
  3. Generate the same specimen in Tide, Summer and Bumble, each light and dark. Cover default, checked, disabled Reset, focus, invalid dates, one/zero counts, long copy, enlarged text, short heights and native scrolling.
  4. Use an unfrozen successor app consumer to adopt that shared source. Remove the corresponding private panel, row, count and full-width-button styles; keep the host controller and column geometry. Do not maintain parallel kit/app implementations.
  5. Compare before/after geometry and states, run palette/ownership/markup checks, and record keyboard, assistive-technology and browser evidence. Preserve this prototype rather than using it as a migration target.

There are no new global type, space, radius, color or motion primitives in this recommendation. Native disclosure, Field errors, neutral Badge and Empty state already have homes. The next implementation should consolidate them, not create alternate families.

Evidence and limits

The review is grounded in the approved Unified Search 1.0.2 prototype, its controller/styles, the existing component registry and the kit's adoption rules. Its archive contains 72 preserved files. The original 180 maintained-kit files also remain unchanged.

Existing browser evidence is Chromium. Firefox/Safari testing remains deferred at the user's request; physical keyboard/device and screen-reader verification remain adoption work. This review does not claim those checks passed.
